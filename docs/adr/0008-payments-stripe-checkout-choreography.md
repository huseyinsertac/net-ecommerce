# ADR-0008: Payments with Stripe Checkout, webhook plus reconciliation, and a fake gateway the demo can refuse

Status: Accepted. Date: 2026-11-26

## Context

Checkout has to charge a card without VoltLane ever touching card data, survive duplicate and late webhooks, and run in three places: automated tests, a local compose stack with no Stripe account, and the public demo, which must never charge a real card. Ordering, Catalog, Basket and Payments are separate modules that coordinate only through integration events (ADR-0004).

## Decision

**The flow is choreographed.** `OrderPlaced` (Ordering) is consumed by Catalog, which reserves stock and answers `StockReserved` or `StockReservationFailed`, and by Basket, which removes the ordered lines. `StockReserved` makes Payments open a payment session; `StockReservationFailed` makes Ordering cancel the order. Payments then publishes `PaymentSucceeded`, `PaymentFailed` or `PaymentExpired`: Ordering marks the order paid or cancels it, and Catalog commits the reservation or releases the stock. No component owns the whole flow, and every reaction is an idempotent inbox handler.

**Stripe Checkout (hosted page), not the Payment Element.** The browser is redirected to a Stripe-hosted page and returns to us. Card entry, 3-D Secure, localisation and PCI scope stay with Stripe, and there is no payment form to build or secure. The cost is a visible redirect and less control over the look, which is the right trade for a portfolio shop whose subject is the backend flow. Sessions are created in `payment` mode, limited to cards, with the idempotency key `checkout-session-{orderId}`, so a retried handler gets the session it already made. The Stripe client has a 15-second timeout per attempt (the SDK retries, so a call can take about 45 s), because session creation runs inside the inbox/outbox transaction.

**The frontend polls; no SSE.** Before the redirect, the SPA polls `GET /api/ordering/orders/{id}/checkout-status` every 500 ms for up to 30 seconds, until the stock is reserved and the payment URL exists. After the shopper returns, the order page polls `GET /api/ordering/orders/{id}` every second for up to 30 seconds (10 seconds after a cancelled checkout) until the order leaves Placed. An order page opened any other way while the order is Placed asks for the checkout status once and offers "Pay now" if the session is still open. Status changes arrive within a few seconds (webhook plus the outbox hops), a poll is a plain GET that works through Caddy and in tests, and nothing holds a connection open. SSE or SignalR would add a stateful connection, reconnect logic and a second delivery path for a handful of updates per order.

**Webhooks are verified and deduplicated.** `POST /api/payments/stripe/webhook` is anonymous and not rate-limited, so its body is capped at 64 KB (413 beyond that, from the Content-Length or while reading) before it checks the `Stripe-Signature` header against `Stripe:WebhookSecret`. Each Stripe event id is stored in `ProcessedWebhookEvent`, so a redelivery is a no-op. Four events are handled: `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed` and `checkout.session.expired`. The route is mapped only when the Stripe provider is active.

**Expiry has one source of truth: Stripe.** A payment has a local deadline (`Payments:Timeout`, 30 minutes by default). A background job (`Payments:ExpiryScanInterval`, one minute) finds overdue Pending payments and asks the gateway for the session state before deciding: paid becomes `PaymentSucceeded` (a lost webhook is repaired here), an open session is expired through the API and becomes `PaymentExpired`, an already expired one is recorded as expired, and a completed but not yet paid session (Processing) is left Pending until its webhook arrives. With Stripe we never mark a payment expired on our clock alone, so a customer who pays in the last second is not cancelled. Two cases do use the clock alone: the Fake gateway, which has no session to ask, and a payment opened by a provider that is no longer configured, which cannot be asked.

**`expires_at` is rounded so retries stay idempotent.** Stripe refuses a session that ends sooner than 30 minutes from its own clock, and a reused idempotency key must carry byte-identical parameters. The gateway sends the local deadline plus one minute, rounded up to the next 5-minute step, so a retry a few seconds later produces the same request. If a retry still crosses a step, Stripe answers `idempotency_error`; the earlier session was never saved, so nobody holds its URL, and the gateway opens a fresh one under a suffixed key. The session can outlive the payment by a few minutes; the expiry job closes it. With Stripe, `Payments:Timeout` must be between 30 minutes and 23 hours.

**A fake gateway, and production refuses it by default.** `Payments:Provider` is `Fake` or `Stripe`. The Fake gateway sends the customer to a simulated payment page in the SPA, so tests, local development and the compose stack need no account or network. In Production the API refuses to start with the Fake provider unless `Payments:AllowFakeProviderInProduction` is `true`. The local `docker-compose.yml` runs as Production and opts in; `docker-compose.prod.yml` sets `Payments__Provider: Stripe` and never sets the flag, so a missing or mistyped provider on the server fails at startup instead of silently serving a fake payment page. Stripe accepts only test-mode keys (`sk_test_` secret or `rk_test_` restricted, which needs just Checkout Sessions: Write) and `whsec_` webhook secrets, in every environment, enforced by options validation at startup (messages name settings, never values). A live key cannot be configured by accident, so the public demo cannot charge a real card.

**Basket lines are removed on `OrderPlaced`, not on payment.** The order owns those lines from that moment, so the customer cannot edit or double-order them while paying. If the order is later cancelled, the basket stays empty and the customer rebuilds it. We chose that over keeping lines "pending" in the basket, which would need a second event round trip and a way to reconcile edits made while payment was open.

## Consequences

- Card data never touches our servers; the PCI burden stays with Stripe.
- Payment confirmation is eventually consistent. The UI shows reservation and awaiting-payment states, and a lost webhook is repaired by the expiry job rather than leaving an order stuck.
- Stripe (or the Fake page) decides money state; our `Payment` row follows it.
- Known gaps, parked on purpose:
  - **Payment success on a cancelled order.** If an order was cancelled (for example it timed out) and a payment still succeeds, the reaction logs it at Error and leaves the order Cancelled. A gateway success for a payment that already Expired or Failed is logged at Error by Payments itself ("needs a refund"), since no `PaymentSucceeded` follows. Refunding is Milestone 2.
  - **Stuck reservations.** If a payment session never opens (Stripe unreachable past the retry budget), the stock stays reserved until the nightly demo reset arrives in Plan 5.
  - **Async payment methods.** Sessions accept cards only, so this should not arise. If a session still completes unpaid, it is mapped to Processing: the expiry job leaves it Pending (it can no longer be expired at Stripe) and the `async_payment_*` webhooks decide. Those are handled but untested against a real delayed method.
- **When to revisit:** real money (live keys, refunds, disputes, a reconciliation report), or customers abandoning the Stripe page often enough that releasing stock sooner matters (a shorter timeout).
